# Identity and access

ballware uses **Keycloak** as its OAuth2/OIDC identity provider. The
`ballware-keycloak` repo builds on Keycloak **26.8.2** and adds ballware
extensions (custom token mapper, user/role REST APIs, Keycloakify
theme).[^1] Backend services validate Keycloak access tokens; authorization
inside services is **scope policies plus a `right` claim** derived from realm
role attributes.[^2]

## Clients

Two realm configurations are evidenced on `main`, and they are not identical:

| Client | Where defined | Type | Purpose |
| --- | --- | --- | --- |
| `ballwareweb` | keycloak repo export **and** compose realm template | public (PKCE; redirects `https://localhost:3000/signin-oidc`, `https://app.ballware.de/signin-oidc`) | Angular web client login[^3][^4] |
| `storage`, `meta`, `generic`, `ml`, `reporting` | compose realm template only | confidential, service accounts | service-to-service calls (client credentials)[^4] |
| `account`, `account-console`, `admin-cli`, `security-admin-console`, `broker`, `realm-management` | both | Keycloak built-ins | Keycloak administration (`admin-cli`/`security-admin-console` carry the `kc-admin-api` scope in the 26.8.2 export)[^3] |

:::caution Status: not consistent across environments
The committed **production-oriented export** (`ballware-keycloak/import/ballware-realm.json`)
contains **only** `ballwareweb` plus Keycloak built-ins — no confidential
service clients, and `serviceAccountsEnabled` is false for every client. The
**evaluation realm template** (`ballware-docker-compose/realms/ballware-realm.tpl`)
adds the confidential service clients with `${*_CLIENT_SECRET}` placeholders.
How production provisions its service clients is not documented in the
in-scope repositories.[^3][^4]
:::

## Scopes and audience

- Exported realm scopes: `metaApi`, `serviceApi`, `storageApi`, `documentApi`,
  `mlApi`, `identityApi`, `messagingApi`, `kc-admin-api` (plus Keycloak
  built-ins).[^3]
- The evaluation template adds `genericApi` and `schemaApi` (the latter
  described as "Access to generic schema API").[^4]
- Audience mappers on `ballwareweb` **and** on every service client stamp the
  custom audience **`metaApi`** into access tokens; all services in the compose
  stack validate exactly this audience (`Authorization__Audience`).[^3][^4][^2]

## Claims

Tokens carry, among standard claims:[^3]

- `sub` — Keycloak user id
- `tenant`, `person`, `allowed_tenant` — from the same-named user attributes
  (standard usermodel-attribute mappers; `allowed_tenant` multivalued)
- `right` — multivalued rights, produced by the custom mapper (below)

There is **no `unit` claim** in any current realm or service configuration;
treat it as legacy if encountered in older material.[^3][^4]

### Rights from realm roles

Right strings follow `<application>.<entity>.<action>`, e.g. `meta.entity.view`
or `identity.role.add`. They are stored as the `right` **attribute on realm
roles**, next to a `tenant` attribute (`*` or a tenant GUID). The custom SPI
provider `ballware-token-mapper` resolves the user's realm roles, keeps those
whose role-attribute `tenant` equals the user's `tenant` attribute (or `*`),
and copies their `right` attributes into the `right` claim (with
`{{userattribute}}` placeholder substitution).[^1][^5]

Exported roles show the pattern: `Administrator` (`right` attributes spanning
`meta.*`, `identity.*`, `tenant.*`; `tenant = *`) and `Globaler Tenant
Administrator` (`tenant.*` rights; tenant attribute includes the seeded admin
tenant GUID — see [Tenancy](/docs/tenancy)).[^3]

Management of users and roles goes through Keycloak **custom REST endpoints**
`/realms/ballware/ballware-user-api` and `/realms/ballware/ballware-role-api`
(all/byId/new/save/remove/selectlist/selectbyid; the user API also offers a
`POST tenant?tenant=` switch guarded by `allowed_tenant`). They authorize
against `right` claims like `identity.user.view` or `tenant.role.edit`,
because admin-API access via protocol-mapper roles is disabled since Keycloak
26.7.1.[^1][^6]

## How services enforce access

Each service configures JWT bearer authentication against the Keycloak realm
and applies authorization **policies named exactly like the required scope**;
most endpoints are dual-scoped (user token **or** `serviceApi`), and
service-scoped routes take an explicit `tenantId` in the path:[^2]

| Service | User-facing policy | Service policy |
| --- | --- | --- |
| meta | `metaApi` | `serviceApi` |
| generic | `genericApi`, `metaApi` | `serviceApi`, `schemaApi` |
| storage | `storageApi` | `serviceApi` |
| ml | `mlApi` | `serviceApi` |
| document (reporting) | `documentApi` | `serviceApi` |

Beyond scopes, entity-level **rights** from the `right` claim are checked per
application/entity/action, extended by per-entity `RightsCheckScript`
(JavaScript) evaluated with Jint in the generic service and compiled
client-side in the web client.[^2] See [Metadata model](/docs/metadata-model).

## Web client configuration (env var names)

The web client is configured entirely through `BALLWARE_*` variables
(`BALLWARE_IDENTITYURL`, `BALLWARE_METAURL`, …, `BALLWARE_CLIENTID`,
`BALLWARE_IDENTITYSCOPES`, `BALLWARE_TENANTCLAIM`, `BALLWARE_USERNAMECLAIM`);
its SSR server signs users in through a Keycloak OIDC provider configured from
the same names.[^7] Keycloak-side env names of operational relevance (values
never documented): `KC_DB*`, `KC_HEALTH_ENABLED`, `KC_METRICS_ENABLED`,
`KC_HTTPS_CERTIFICATE_FILE`/`KC_HTTPS_CERTIFICATE_KEY_FILE`,
`KC_HOSTNAME_ADMIN_URL`, `KC_BOOTSTRAP_ADMIN_USERNAME`/`KC_BOOTSTRAP_ADMIN_PASSWORD`
(dev only), `KC_PROXY_HEADERS` (26.x guidance).[^1][^4]

:::caution Status: inconsistent proxy config in the evaluation stack
The compose stack still sets the deprecated `KC_PROXY` variable, while the
Keycloak repo's 26.8.2 notes require `KC_PROXY_HEADERS=x-forwarded` behind a
load balancer (`KC_PROXY` was removed in Keycloak 26.0).[^1][^4]
:::
